GitHub Actions for small, fast pull requests

Delivery Guardrails

Two workflows you copy into your team's repos. One stops big or stale pull requests from merging. The other tells Slack when work is stuck before it reaches UAT. Ages count working hours only, so nights and weekends never count against anyone.

Set it up View the repo
What you get

Two guardrails

pr-rules.yml

PR rules

Blocks merging
  • Fails a pull request that changes more than 500 lines. Lock files, snapshots and generated code don't count.
  • Fails a pull request whose work started more than 8 working hours ago, re-checked every hour.
  • The tech lead can allow one with the size-exception or age-exception label.
delivery-alerts.yml

Delivery alerts

Posts to Slack
  • Pull requests open more than 6 working hours, grouped by who must act: reviewers or the author.
  • Merged pull requests not on UAT within 7 working hours, and a failed latest UAT deployment.
  • Repos with no UAT deployments recorded, so none go unwatched by accident.
The clock

Only working hours count

By default the clock runs 09:00–18:00 IST, Monday to Friday, and skips holidays you list. A pull request opened at 4pm gets 2 hours that day, then the clock resumes at 9am the next working day.

No servers, no database, no dependencies: two small Node scripts and the built-in GitHub token. Your workflows pin a release, so updates here never change your checks until you choose to.

Setup · in each repo

Block big or old pull requests

  1. Copy the workflow

    Copy templates/pr-rules.yml (shown below) to .github/workflows/pr-rules.yml on the repo's default branch. The hourly re-check only runs from there.

  2. Create the exception labels

    gh label create size-exception --color FBCA04 --description "Allowed over the line limit; tech lead approved"
gh label create age-exception  --color FBCA04 --description "Allowed over the age limit; tech lead approved"

  3. Open any pull request

    The two checks need to report once before GitHub lets you mark them as required.

  4. Make the checks required

    Settings → Rules → Rulesets → New branch ruleset. Target the default branch, turn on Require status checks to pass, add pr-rules/size and pr-rules/age, and set enforcement to Active. Or run this from the repo folder:

    gh api -X POST "repos/{owner}/{repo}/rulesets" --input - <<'JSON'
{
  "name": "PR rules required",
  "target": "branch",
  "enforcement": "active",
  "conditions": { "ref_name": { "include": ["~DEFAULT_BRANCH"], "exclude": [] } },
  "rules": [
    { "type": "required_status_checks", "parameters": {
      "strict_required_status_checks_policy": false,
      "required_status_checks": [ { "context": "pr-rules/size" }, { "context": "pr-rules/age" } ] } }
  ]
}
JSON
Setup · once, in one repo

Alert on stuck work

  1. Copy the workflow

    Copy templates/delivery-alerts.yml to .github/workflows/delivery-alerts.yml in one of your team's repos.

  2. List your team's repos

    gh variable set TEAM_REPOS --body "your-org/orders-api your-org/orders-web your-org/refund-worker"

  3. Add a read-only token

    Create a fine-grained token with access to only those repos and read-only Pull requests, Deployments and Contents. Save it as the secret TEAM_READ_TOKEN. If you watch only the repo the workflow lives in, skip this step.

  4. Connect Slack

    Create an incoming webhook for your team channel and save it as the secret SLACK_WEBHOOK.

  5. Record UAT deployments

    If you deploy with GitHub Actions, give the UAT job environment: uat and GitHub records every deployment. With Jenkins, Argo CD or similar, add this step after each UAT deploy, using state=failure when it fails:

    id=$(gh api -X POST "repos/$REPO/deployments" --input - --jq .id <<JSON
{"ref": "$DEPLOYED_SHA", "environment": "uat", "auto_merge": false, "required_contexts": []}
JSON
)
gh api -X POST "repos/$REPO/deployments/$id/statuses" -f state=success

  6. Run it once

    Open the Actions tab, choose Delivery alerts and click Run workflow. After that it runs hourly, Monday to Friday, 09:30–18:30 IST.

Settings

Change the limits without editing YAML

Set these under Settings → Secrets and variables → Actions → Variables. Anything you don't set uses the default. If you change the time zone, change the cron lines in the workflows too; cron runs in UTC.

VariableDefaultMeaning
MAX_LINES500Most changed lines in one pull request
MAX_AGE_HOURS8Most working hours since the work started before merging is blocked
AGE_FROMoldest-commitOr pr-opened, a clock nobody can change
IGNORE_PATHSlock files, .snap, generated/Regular expression for files that don't count towards the limit
TEAM_REPOSthis repoSpace-separated owner/repo list to watch
MAX_PR_HOURS6Alert on pull requests open longer than this; keep it below MAX_AGE_HOURS so the alert comes first
MAX_UAT_HOURS7Alert on merged pull requests not on UAT after this
UAT_ENVIRONMENTuatDeployment environment name to watch
AGE_CLOCKworkingworking, or calendar to count every hour
WORK_TIMEZONEAsia/KolkataAny IANA time zone, such as Europe/London
WORK_START / WORK_END09:00 / 18:00Working hours, 24-hour clock
WORK_DAYSMon,Tue,Wed,Thu,FriWorking days
HOLIDAYSnoneDates to skip, such as 2026-12-25,2027-01-26
On purpose

What it doesn't measure

People

It reports stuck work, not individuals. Don't rank anyone by alerts, and don't measure "pull requests per developer".

Quality

A small, fast pull request can still be wrong. Code review and tests stay essential.

Production

It stops at UAT. Track production with your DORA metrics: deployment frequency, lead time, change failure rate and recovery time.

Troubleshooting

When something looks wrong

SymptomCause and fix
pr-rules/size isn't offered as a required checkThe checks haven't reported yet. Open a pull request first.
No checks on pull requests from forksThe built-in token is read-only for forks. Work in branches of the same repo.
A repo is listed under "No uat deployments recorded"No successful deployment with that environment name. Check the name and that your pipeline records deployments.
GitHub GET … returned 404TEAM_READ_TOKEN can't see that repo. Add it to the token.
Slack returned 404: no_serviceThe webhook was removed or mistyped. Create a new one and update the secret.
The age check doesn't turn red overnightExpected: the working clock doesn't move outside working hours.
Rollout

Four weeks to switch it on

WeekStep
1Install both workflows on one squad's repos. Require the size check; leave the age check visible but not required.
2Watch how often pull requests cross the limits. Adjust IGNORE_PATHS and the hours.
3Connect Slack, and agree who acts on each alert stage.
4Review the numbers with the team, then require pr-rules/age too.
